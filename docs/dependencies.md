On 2026-10-25 a fresh scan against the current RustSec and npm advisory databases found two new Rust findings and nine npm findings; each had a compatible patch release, so no exception was added or renewed. **ctutils 0.4.3 to 0.4.4** (RUSTSEC-2026-0385, non-constant-time mask generation and `u128` comparisons) is a transitive dependency of `universal-hash` 0.6.1 through `poly1305` and `chacha20poly1305`; the patch stays inside that crate's declared `0.4` requirement, so no parent changed. **Tokio 1.53.2 to 1.53.3** (RUSTSEC-2026-0386, unsound `AsyncFd` constructors) is the minimum patched release in the pinned 1.53 line; the application does not call `AsyncFd`, and the patch keeps the exact pin, features, and documented `kill_on_drop`/`kill`/`wait` contract above. The npm findings were the development-only `undici` and `serialize-javascript` paths recorded in [decision 0002](decisions/0002-wdio-transitive-advisory-remediation.md): `undici` 6.29.1, 7.30.1, and 8.12.2 per major line and `serialize-javascript` 7.1.3. No shipped artifact links those packages; `pnpm inventory:generate` regenerated the lockfile digests and versions in [the inventory](verification/dependency-inventory.json).

The [toolchain bootstrap](../scripts/dev-toolchain.ts) records these pins and the published digests in one place. It provisions Node, pnpm, and protoc into the gitignored `.tools/` directory, verifies the Node archive against `SHASUMS256.txt`, verifies the protoc and `talosctl` archives against their published SHA-256 values, verifies the Go and Rust versions from `PATH`, never installs system-wide, and fails closed on any mismatch. Its pure helpers and failure paths have deterministic Vitest coverage. `pnpm toolchain:bootstrap` runs it once pnpm exists; before that, `node scripts/dev-toolchain.ts` works from any Node 22 or newer host.

The probe uses the official `client.New`, `client.WithConfig`, `client.WithEndpoints`, `client.WithNodes`, `Client.Version`, `safe.StateWatchKind`, and the Talos `runtime.MachineStatus` resource. `go.mod`/`go.sum` are authoritative; the local build/vet/test/race probe passes under the pinned Go 1.27.3 toolchain. Rust Kubernetes, vault, editor, terminal, charts, routing, and state dependencies likewise belong with their first concrete capability; installing unused packages would not qualify those integrations. See the primary-source compatibility record in [C0.2 evidence](verification/milestone-1.md#c02-dependency-and-harness-research) and the [C4 acceptance/evidence record](verification/milestone-1.md#c4-acceptance-cases).

The Go toolchain moved from 1.27.1 to 1.27.2, and `golang.org/x/net` from v0.58.0 to v0.60.0 (with `x/crypto` v0.57.0, `x/sys` v0.48.0, and `x/text` v0.42.0), on 2026-10-09 in response to `govulncheck` findings GO-2026-6617 (HTTP/2 HPACK encoder race, fixed in `x/net` v0.60.0 and Go 1.27.2) and GO-2026-6613 (HTTP/1 desynchronization after a 2xx CONNECT, fixed in Go 1.27.2). Both reached the helper only through the gRPC transport behind the Talos client, and the scan reports no findings after the upgrade.

On 2026-10-22 the Go patch moved from 1.27.2 to **1.27.3**, the current stable release, which shipped on 2026-10-19 with security fixes to `crypto/x509` ([Go release notes](https://go.dev/doc/devel/release#go1.27.3)). The installed 1.27.2 standard library was called through `internal/protocol/frame.go` and reported GO-2026-6809 (distrusted intermediate certificates), so the helper's module graph and the whole Go gate run were re-checked under 1.27.3 with the same module versions; `govulncheck` 1.8.0 then reported no called vulnerability. The toolchain archive was verified against the SHA-256 published by the Go release list before use. No Go module version changed.

Tokio **1.53.3** (MIT) is now a direct Rust dependency for bounded helper-process I/O, asynchronous deadlines, and process reaping ([crate metadata](https://crates.io/crates/tokio/1.53.3)). It uses the application's existing Tokio runtime; no second runtime or shell plugin is introduced. The process supervisor uses Tokio's documented [`kill_on_drop`](https://docs.rs/tokio/1.53.3/tokio/process/struct.Command.html#method.kill_on_drop), `kill`, and `wait` behavior, and explicitly awaits child exit on owned cleanup paths. The exact pin and feature set are in [Cargo.toml](../src-tauri/Cargo.toml) and [Cargo.lock](../src-tauri/Cargo.lock).

F2 pins the Rust Kubernetes client, resolved from the crates.io index and the fetched crate sources on 2026-10-11: **kube 4.2.0** (Apache-2.0, declared MSRV 1.88.0, so it is inside the Rust 1.99 line) with the `client`, `config`, `rustls-tls`, and `ring` features, **k8s-openapi 0.28.0** with exactly one compile-time schema feature, `v1_36`, **http 1.5.0**, and **pem 3.0.6** to match kube-client's own requirement. `kube` is the upstream adapter the design selects; `k8s-openapi` supplies the typed schema for that single version. F4 adds only kube 4.2.0’s `runtime` feature for its supported watcher list/watch recovery, which handles opaque resource-version bookkeeping and atomic `Init`/`InitDone` relists. This feature adds the pinned `kube-runtime` 4.2.0 dependency; no second schema feature is enabled. See the [pinned watcher documentation](https://docs.rs/kube/4.2.0/kube/runtime/fn.watcher.html). F4 also pins **tower 0.5.3** (no default features) for the `Service`/`Layer` boundary, **http-body 1.1.0** for the streaming body wrapper, and **bytes 1.12.1** for zero-copy 64 KiB slices. The wrapper applies the 15-second timeout only until response headers arrive, then rejects a newline-delimited watch event larger than 2 MiB before kube deserializes it; it imposes no idle read timeout on the established body. These are direct pins in `Cargo.toml` and the lockfile. `tokio-rustls` and `rcgen` are declared with `default-features = false` plus the `ring` provider so the binary carries one Rustls crypto provider; both are optional and reachable only through the `native-test` feature, and `pnpm production:check` asserts `rcgen` is absent from the default graph. See [decision 0012](decisions/0012-kubernetes-client-session-boundary.md) for the client construction and credential-session contract.

F3 uses **sha2 0.10.9** as a Rust development dependency to verify the checked fixture's kubeconfig CA fingerprint before making any Kubernetes API request. It is not part of the application dependency graph.

The F6 editor pins **monaco-editor 0.57.0** (MIT) and **yaml 2.9.1** (ISC). `monaco-yaml` 5.5.1 is the current upstream Monaco YAML plugin, but its released worker path still calls the `createWebWorker({ moduleId })` API removed in Monaco 0.55 and its `dispose()` does not stop its worker manager. F6 therefore uses the current editor with a small owned worker around the upstream YAML parser instead of maintaining a fork; [decision 0019](decisions/0019-offline-yaml-editor-worker.md) records the alternatives, bounds, diagnostics, and cleanup contract. The editor is imported from `monaco-editor/editor/editor.api`, not the all-language root, and both workers are emitted as same-origin Vite assets. `dompurify` is overridden to **3.4.17** because the editor's pinned 3.4.15 has published advisories on the `monaco-editor > dompurify` path; the override is a patch-level security refresh. The editor's inert schema strategy does not fetch or expand any remote schema. The measured lazy chunks are observations for F10, not performance budgets.

F7 pins the specialized-view libraries from their primary release sources on 2026-10-25. **xterm.js 6.0.0** (`@xterm/xterm`, MIT) is the current stable xterm release, and **`@xterm/addon-fit` 0.11.0** (MIT) is published from the same monorepo commit (`f447274f430fd22513f6adbf9862d19524471c04`, recorded in both package manifests), so the addon declares no peer range and matches the pinned terminal. The feasibility surface uses the documented `Terminal` options (`cols`, `rows`, `scrollback`, `screenReaderMode`, `fontFamily`, `fontSize`, `theme`) plus `write(data, callback)`, `reset()`, `resize()`, `dispose()`, and the addon's `fit()`/`proposeDimensions()`; it does not enable `allowProposedApi` and adds no link, clipboard, WebGL, or image addon. Retained output is limited to 1,048,576 UTF-8 bytes and 10,000 logical lines, the emulator to 20–200 columns × (5–50 visible + 1,000 scrollback) rows, and replay to one 32 KiB canonical write (≤ 64 KiB after CRLF rendering expansion) awaiting its real callback with a 5-second stall deadline. xterm's own stylesheet (`css/xterm.css`) and uPlot's `dist/uPlot.min.css` are bundled by Vite, and xterm's runtime style injection is covered by the existing `style-src 'self' 'unsafe-inline'`; `script-src` stays `'self'`, so neither library may add `eval`/remote code.

uPlot 1.6.32 evaluates `new Intl.NumberFormat(navigator.language)` while its module body runs. WebKitGTK reports the POSIX locale `C` on a host without a configured locale, which WebKit's stricter ICU rejects with a `RangeError`, so the chart module would never evaluate. The lazy chart loader therefore supplies `en-US` for that import only when the reported tag is unsupported and restores the WebView value immediately afterwards ([chartLocale.ts](../src/features/charts/chartLocale.ts), with deterministic regression tests). This is a narrow upstream-compatibility workaround found by the F7 native run, not a locale, dependency, or global setting change.

**uPlot 1.6.32** (MIT) is the current stable uPlot release. The chart uses its `uPlot.Options`/`AlignedData` types and the constructor, `setData`, `setSize`, `redraw`, and `destroy` methods, with at most 8 value series × 2,000 newest aligned samples and 80-code-point metadata. Both packages are ESM, declare no Node built-ins or peer dependencies, and are dynamically imported so Home and the other surface never load them. Their MIT license text joins the installer notice bundle; neither ships a `NOTICE` file. F8's [notice-packaging packet](plans/foundation-finish/07-f8-dependencies-notices-security.md) and F9's installed-artifact review remain separate work, so this pin does not close C7.

0004](decisions/0004-native-vault-integration.md). Linux Secret Service has a

remain open for C8.

**1.3.0** is enabled with only its deserializer feature, with parser budgets

F6's Monaco Editor is MIT and the YAML parser is ISC; the overridden `dompurify` is MPL-2.0 OR Apache-2.0. Monaco ships a `ThirdPartyNotices.txt` that the installer notice packaging must redistribute even though the generated inventory only detects files named `NOTICE`; that packaging remains a release task. The Rust desktop/build crates are Apache-2.0 OR MIT. Upstream packages are actively released; registry metadata and successful builds establish this initialization's compatibility, not the later platform/cluster qualification.

The WebdriverIO service/plugin packages are MIT; `tauri-plugin-wdio` is MIT OR Apache-2.0 and `tauri-plugin-wdio-webdriver` is MIT. Their transitive obligations are in the generated inventory below.

`pnpm inventory:generate` writes [the generated inventory](verification/dependency-inventory.json) and `pnpm inventory:check` fails on any drift, so the inventory is never hand-edited. It is schema version 2 and records the toolchain pins plus the SHA-256 of `pnpm-lock.yaml`, `src-tauri/Cargo.lock`, and `helper/go.sum`, then one sorted entry per dependency: 535 npm packages from `pnpm licenses list --json`, 614 registry Cargo packages from `cargo metadata --locked --format-version 1` (workspace members are first-party code, not an obligation), and 143 Go modules from `go list -m -json all`, of which the 35 that actually contribute packages to the helper binary are marked `linked`. Each Go entry names its license only when exactly one canonical marker set matches its license text — 35 of 35 linked modules resolved — and otherwise reports `unknown`. The 108 graph-only modules are reported as `unobserved` and their license files are never read: a graph-only module is in the module cache only when unrelated work downloaded it, so reading it would make the inventory differ between machines and fail the drift gate on a clean runner. `unobserved` is therefore not a license claim. A linked module with no extracted source is a generator error.

Redistributed notices follow from that inventory: the packages carrying a `NOTICE` file are `@playwright/test`, `playwright`, `playwright-core`, `typescript`, `@typescript/typescript-linux-x64`, `bare-path` (all dev-only), and the linked Go modules `go.yaml.in/yaml/v4` and `google.golang.org/grpc`, which must ship with the packaged helper. MPL-2.0 covers 18 entries overall, including the linked Go modules `github.com/cosi-project/runtime`, `github.com/hashicorp/errwrap`, and `github.com/hashicorp/go-multierror`; MPL is file-level copyleft, so any modification to those files must be documented and the source made available. The only npm package with no declared license is `css-value@0.0.1`, which arrives solely through the WebdriverIO development chain that the production-exclusion gate keeps out of shipped artifacts. Cargo expressions include MPL-2.0, Unicode data licenses, and LLVM exceptions, and two crates offering LGPL resolve through their MIT/Apache alternative. Final installer notice packaging remains a release task.

Use `pnpm audit`, `cargo audit --file src-tauri/Cargo.lock`, `pnpm audit:go`, and `pnpm advisories:check` for advisories; CI also runs Trivy over both lockfiles and `helper/go.mod`, and its exceptions follow [CI/release](ci-release.md). Record any finding's applicability rather than silently excluding it, and keep the verification record on the actual scan output.

`pnpm inventory:check` is a Linux-only CI step because the npm license listing includes platform-specific optional packages (`@typescript/typescript-linux-x64`, `lightningcss-linux-x64-gnu`), so the committed inventory is the Linux view of the graph; per-platform inventories belong with the installer notice packaging.

## Desktop configuration

The main capability grants only the named application settings, credential-import, helper-status, Kubernetes credential/session, and Talos-probe commands documented in [application IPC](protocol/application-ipc.md). It grants no generic shell, filesystem, or remote-navigation access; the backend alone launches the bundled helper and reads selected credential files. The CSP permits bundled scripts and Tauri's IPC origins only. Inline **styles** remain permitted: the stylesheet itself is now a bundled static file, but Skeleton's Zag machines and Bits UI apply inline style attributes for positioning; executable inline scripts and remote assets remain blocked. The Linux native-test build rendered the Svelte shell under this CSP on 2026-10-11 ([0008](decisions/0008-svelte-skeleton-renderer.md)). F6 added no CSP directive: the editor and both workers use bundled same-origin files under the `script-src 'self'` worker fallback, and the native suite observed inline and unauthorized-origin script denial plus no remote editor request. Cross-platform editor/worker verification and installed-package rows remain with documents 08 and 10.

The [canonical project icon](../assets/app-icon.png) was generated with the built-in image generation tool. Its prompt and provenance are in [assets/README.md](../assets/README.md). The pinned Tauri CLI converts the retained bitmap into PNG/ICO/ICNS assets through `pnpm icons:generate`; `pnpm icons:check` compares generated bytes. ICNS chunk ordering is canonicalized without changing image payloads, resolving the CLI nondeterminism observed at initialization. Release-only configuration enables draft-preview installer builds; the complete helper/signing/platform qualification remains foundation work. See [CI/release setup](ci-release.md).
