## 4. Contracts and resource limits

The following are proposed C5 implementation defaults, not current APIs. Refine them with compatibility evidence and producer/consumer tests before accepting F2–F4. Keep [application IPC](../protocol/application-ipc.md), [helper v1](../protocol/helper-v1.md), and [storage v1](../storage/storage-v1.md) synchronized with implementation.

- Rust owns Kubernetes clients, decrypted credentials, session identities, watch tasks, and authoritative projections. The Go helper has no ordinary Kubernetes browsing role.
- Resolve credentials by a backend-issued opaque handle. A handle is not an authorization grant: validate its kind, profile association, current storage mode, and caller capability before use. No credential bytes, filenames, raw kubeconfig, tokens, or SDK objects cross renderer IPC.
- Construct the client from an explicitly selected, validated in-memory kubeconfig. Never use ambient default/in-cluster configuration or reread arbitrary paths. Build a supported-field configuration rather than handing the raw document to an SDK that may interpret ignored fields. Reject exec/auth-provider/external credentials and insecure TLS before any SDK action. No external credential-provider trust workflow is introduced here.
- Probe namespaced Pods with server-side label/field selectors validated against the pinned API. Project only bounded name, namespace, UID, resource version, phase, and readiness summary. Do not project arbitrary annotations, Pod specs, environment, addresses, or raw error/status messages.
- Keep session, namespace, resource, selectors, and page identity explicit in every request/cache key; subscription ID and sequence accompany every event. Resource versions are opaque strings; application sequence numbers are decimal strings backed by unsigned 64-bit integers. Recreated objects are distinguished by UID.
- Until milestone 2 links Talos and Kubernetes access in one cluster profile, the two adapters admit sessions separately. The Kubernetes adapter holds at most four sessions; the existing four-session Talos credential store is unchanged. Do not refactor the Talos store into a shared counter in this phase. This refines the original plan's global four-session default, which assumed linked profiles; record it in application IPC.
- Allow at most seven Kubernetes read subscriptions. With the single active Talos probe, that keeps the global total at eight without coupling the adapters. Allow at most 32 admitted Kubernetes requests. Admission must reject excess work before spawning or queuing it. Document the single Talos probe beside these limits; the total is a ceiling, not a claim of helper multiplexing.
- The Talos probe keeps its documented cap of 256 forwarded status events per subscription. A replacement snapshot after a reconnect continues the same subscription's sequence and counts toward the cap. Reaching the cap ends the subscription with a terminal outcome that the view does not present as current. Do not raise the cap to lengthen a test or a measurement; a change needs the protocol documents and producer/consumer tests.
- Start with 200 items per list page, 10,000 retained projected objects per active probe, and 2 MiB per decoded list page or watch event. Enforce a response-byte bound before decoding, per-field bounds (starting at 253 bytes for a name, 63 for a namespace, 64 for a UID, 128 for a resource version, 32 for a phase, and 1 KiB for each selector), and a 16 MiB projection budget per session, including replacement generations. A hit on any cap yields explicit bounded/partial status; it cannot become a healthy complete snapshot. Keep server continuation state bounded and backend-owned.
- Bound each subscription by both 64 queued messages and 8 MiB, and deliver at most 200 projected items per batch. Tauri channel send success does not prove consumption: implement bounded acknowledged delivery or an equivalently demonstrated flow-control contract. A batch unacknowledged after five seconds is an ack timeout. Overflow/ack timeout marks the projection stale, stops delivery, and requires bounded resync; terminal/control outcomes cannot be silently dropped.
- Each attempt at a request (a list page, a discovery call, or a watch establishment) has a 15-second deadline. A complete multi-page snapshot or relist has 60 seconds, retries included. Transient read/reconnect failures have at most three total attempts, with 0.5/1-second backoff and ±20% maximum jitter. Auth/permission/input/TLS failures do not retry. A 410 relist is a new snapshot generation, not a retry reset: after three consecutive relists with no watch event applied between them, mark the projection stale and require an explicit reconnect.
- Watch cancellation acknowledges stopped delivery within two seconds and joins owned tasks. Cancel, close, channel loss, namespace/query replacement, window shutdown, and failed startup release admission permits, clients, buffers, and task handles. View navigation retains the credential session but stops a Kubernetes watch whose view is no longer active. Preserve the existing shell-owned Talos probe lifetime and visible status.

Test at each bound and one beyond it. Retry clocks and transport faults should be injectable; actual task/process/socket cleanup must also be observed in integration tests.

### F1a — Detect a stalled Talos stream

**Maps to:** C4, FND-004, and the [0011 amendment](../decisions/0011-talos-stream-reconnect-and-generations.md#amendment--2026-10-12-live-evidence-and-owner-decision). **Prerequisite:** F1 closed. The [finish series](foundation-finish/01-f1a-live-stall-rows.md) gives step 4 its own session, ahead of F3's.

**Behavior:** a subscription whose pinned node stops responding without breaking the connection becomes stale within a bounded, documented window, then follows the existing reconnect budget to a replacement snapshot or terminal `talos_unavailable`. An idle stream on a healthy node stays current.

1. Decide the mechanism in a new decision record before writing code, and have it supersede 0011's stall-detection consequence. Read the pinned official client and the Talos API proxy behavior from primary sources first. State what is checked, over which path, the detection window, and why a `MachineStatus` watch that is merely idle is not taken for a stall. F1 part 3 measured the frozen-worker and reboot behavior with a throwaway driver whose output was not kept; reproduce any measurement the decision relies on.
2. Implement it in the helper, on the subscription's node-pinned session from 0007. A detected stall is an interruption: emit the stale marker, then spend the same three-attempt budget, with no second budget and no change to the generation or sequence rules. Each check obeys section 4's 15-second attempt deadline, at most one check per subscription is in flight, and cancellation during a check ends promptly. A permission or TLS failure of a check is terminal and is not retried. Do not route a status request through the Rust supervisor during a probe; R3 stays deferred. Update [helper v1](../protocol/helper-v1.md) and [application IPC](../protocol/application-ipc.md) for the changed semantics, and the contract sources if the wire changes.
3. Add deterministic framed tests with scripted sessions and an injected clock: silence with failing checks reaches stale and then exhaustion; silence with passing checks stays current across several windows; a stall that clears recovers under the next generation; cancellation during a check; a terminal check failure; helper exit with a check in flight.
4. Add the live row. Suspend the worker's QEMU process with the already-authorized `SIGSTOP`, expect the stale marker and then `TALOS_UNAVAILABLE` inside the detection window plus the reconnect budget, and resume the worker on every exit path, including a panic; commit `ae67a9c` holds a guard written for that purpose. Observe an idle healthy stream for longer than the detection window as well. In the same change, stop the live cases from blocking the test runtime: `reboot_worker` runs `talosctl reboot` synchronously and waits for the machine to be ready, which took 9 and 16 minutes on 2026-10-12, so the stream under test is not polled for that long. Record any change to the reboot command's form in the allowlist before using it. Re-run every live row, because the harness changes. Pin each outcome, following [0013](../decisions/0013-talos-stream-stall-detection.md#unverified-until-step-4-live-fixture): a held suspend must end `TALOS_UNAVAILABLE`; a suspend released as soon as the stale marker is seen must recover under the next generation; and the reboot row must measure the outage and assert the outcome that length implies, which for a reboot outlasting the stale bound plus the budget is `TALOS_UNAVAILABLE`. Replace the F1 reboot row's either-outcome assertion accordingly.

**Tests/evidence:** Go gates including race tests; Rust supervisor, contract, renderer, and native gates for each boundary whose behavior changes; the live stall, exhaustion, idle, and restoration rows on the allowlisted fixture.

**Exit:** a frozen worker is observed live to go stale and end `talos_unavailable` within the documented bound, and an idle healthy stream is observed to stay current. Until then C4's live retry-exhaustion evidence stays recorded as absent.
